# P5 规划：把「能跑」变成「可复现地证明它能跑」

对应 `2026-10-27-auth-and-user-memory-isolation-design.md` §9 的 P5：

> 本机双账号真实验收、重启验证、HTTPS/回滚和文档 —— 完成口径：验收矩阵通过。

P1 做完了账号、登录态、CSRF、限速；P2 做完了独享客户、服务凭证、银行归属；P3 做完了前端
清场与上下文归属。三批都有各自的测试，但**没有一次是把三个进程都起来、用两个真实账号、从
浏览器和 HTTP 两头一起走完的**。P5 补的就是这一遍，以及把散在四份文档里的口径收敛成一份可
执行的验收手册。

### 0.1 P4 为什么取消（留一句在这里，免得只有设计文档里有）

安全的偏好只能是用户手动保存的：自动提取会把 A 会话的内容搬进 B 会话，正是 P1–P3 花三个
批次消除的串线面。而「去设置页点保存」这个动作在演示和日常使用中都不会被点开。做一个没人
用的功能，不如把力气放在验收和文档上。这个判断由用户 2026-10-28 做出，不是实施层面的取舍。

## 1. 为什么不直接「跑一遍 pytest」就算验收

现有测试全部走 `TestClient`，在**进程内**构造请求。它证明不了 P1–P3 的几条核心结论，因为那
几条恰好落在进程边界上：

| 结论 | 进程内测试为什么证明不了 |
| --- | --- |
| 登录 token 只走 HttpOnly Cookie | `TestClient` 不执行浏览器 Cookie 策略，也不区分 HttpOnly |
| 撤销后**不同 worker** 立即拒绝 | 测试里只有一个进程、一个连接池 |
| 重启后历史还在 | 测试的 schema 是每个用例新建再销毁的 |
| 换人后页面不残留 | 前端 437 条单测跑的是组件，不是真浏览器里的 `localStorage` 与 `BroadcastChannel` |
| CSRF 的 Origin 校验真的挡得住跨站 | 测试自己造 `Origin` 头，造什么就信什么 |

所以 P5 的验收是**三层**，缺一层都不算过：

1. **回归基线**：后端全量 + 银行侧全量 + 前端 `vitest`，证明改动没有把既有行为弄坏。
2. **真实 HTTP 验收**：`_accept/auth_acceptance.py` 打真实端口，带真实 Cookie jar，覆盖
   越权、限速、撤销、归属这些「必须换个身份再试一次」的用例。
3. **手工浏览器**：A11/A12 这类「上一个人的内容会不会闪在屏幕上」只能人眼看。

## 4. 验收脚本设计

### 4.1 位置与依赖

`_accept/auth_acceptance.py`，用 `backend/.venv` 的 python 跑（`httpx` 已在依赖里）。参数：

```
--app-url   http://127.0.0.1:8000
--bank-url  http://127.0.0.1:8001
--only A01,A06      只跑指定用例
--out       _accept/auth-acceptance.md
```

两把钥匙从各自的 `.env` 读，不写进命令行、不写进报告：

- `backend/.env` → `BANK_SERVICE_TOKEN`（A15 直连 8001 用）
- `bank_backend/.env` → `SERVICE_TOKEN` / `OPS_TOKEN`（A15 清库被拒的用例要用错的那把）

### 4.2 三条硬规则

1. **不碰 `user_0001`，不清库。** 两个账号名带随机后缀（`acc_a_<hex8>` / `acc_b_<hex8>`），
   会话自建。跑完只在库里留下两个新用户 —— 那正是验收要的产物，不是垃圾。
2. **失败不中断。** 每条用例返回 `(编号, 标题, 判定, 证据)`，最后汇总成表；一条红了不影响
   后面的用例跑完。中途抛异常记为 `ERROR`，不记为 `FAIL`（两者含义不同）。
3. **不重复造已有测试。** `test_pool_refill.py`、`test_auth_api.py`、`test_context_ownership.py`
   已经覆盖的，脚本只补「必须换进程 / 换身份 / 换 Cookie」才看得出的那部分。

### 4.3 报告形状

```markdown
| 编号 | 判定 | 证据 |
| --- | --- | --- |
| A01 | ✅ | 201 + 201；重名 409 LOGIN_NAME_TAKEN；并发两线程一成一败 |
| A06 | ❌ | GET /conversations/{A} 用 B 的 cookie 返回 200（期望 404） |
```

失败的用例要带 request_id —— 日志里按它一搜就能定位，不用猜。

## 5. 重启验证（A19 的本机部分）

```
1. A 登录 → 建会话 → 发一条消息 → 记 conversation_id、cookie、余额
2. stop.ps1                     断言 8000/8001/5173 端口均已释放
3. start.ps1                    断言三个健康检查 200
4. GET /api/auth/me（旧 cookie） 断言 200 —— 登录态在库里，不在内存
5. GET /api/conversations       断言第 1 步的会话还在，标题与消息数不变
6. POST /api/session            断言 403 DEMO_DISABLED —— 重启不复活演示旁路
7. B 的 cookie 读 A 的会话       断言 404 —— 重启没把归属校验弄丢
8. 银行侧余额                    断言与第 1 步一致 —— 客户池与绑定没丢
```

第 4 条是这次验证的重点：P1 把进程内 `Identity._cache` 删掉之后，「重启就掉线」这个症状
如果出现，说明有人把缓存加了回来却没有跨 worker 撤销。**掉线不是失败，静默放行才是。**

## 6. 手工用例（A11 / A12）

`_accept/README.md` 里写成可照做的步骤，每条都带「看到什么算过」：

- **A11**：A 登录 → 发一条会跑很久的消息（触发 SSE）→ 消息还在流的时候在另一个标签页退出
  并登录 B → 回到第一个标签页。**过**：流被掐断、页面回到登录页、屏幕上不再出现 A 的内容。
  **不过**：B 的界面里冒出 A 的半条回复，或流继续往 B 的页面写。
- **A12**：开三个标签页 → 其中一个退出 → 另外两个在 1 秒内自己回到登录页；刷新任意一个，
  停在登录页而不是闪一下工作台；按浏览器后退，不出现上一个账号的会话列表。

### 7.1 `demo-script.md` 现在是坏的

`_accept/demo-script.md` 的「60 秒自检」里有四条直连 8001 的调用：

```powershell
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8001/api/seed/reset"
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8001/api/seed/demo"
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8001/api/clock"
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8001/api/security/reset-lock"
```

P2 给 8001 加了 `_guard` 中间件：除 `/api/health` 与文档路由外全部要求 `X-Service-Token`，
`/api/seed/*` 另要 `X-Ops-Token`。**这四条现在全部 401。** 演示当天照着这份脚本做自检，会
在第一步就卡住，而报错是 401 不是「文件不存在」，很容易被当成服务没起来。

改法：从 `bank_backend/.env` 读两把钥匙再带上，并把「四条都要带 token」写进注释。

## 8. 明确不做

- **HTTPS / Secure Cookie。** 服务器 443 是 sing-box 的 Reality，占了就没法上网（AGENTS.md
  与 `deploy/README.md` 都写着不能动）。P5 只把这条边界写进文档：**当前部署的登录 Cookie
  在同链路可被窃听，验收结论只在受控网络内成立。** 对外前必须另行设计 TLS 终止。
- **真机部署与回滚演练。** 会真的动服务器和数据库，不在本批次。
- **nginx Basic Auth 口令轮换。** P1 遗留第一条，继续挂着（见 §9）。
- **P4 跨对话偏好。** 已取消，不是延后。

## 9. 遗留（P5 交付后仍然存在）

| 遗留 | 影响 | 建议归属 |

| nginx Basic Auth 口令 `bank/<basic-auth-password>` 明文写在 `docs/deploy-cicd.md` 里且已入库 | 外层门禁等于不存在 | 对外前必须做：换口令 + 改成只存服务器 |

### 11.2 验收过程本身抓到的缺陷

规划里写「P5 是验收批次，不改产品代码」，实际动了两个产品文件（`routes.py`、
`security.py`）、三个测试文件和一批文档 —— 因为验收真的抓到了问题，而这正是这一批的目的：

1. `require_trusted_origin()` 只覆盖 auth 路由，业务接口没有 Origin 校验 → 移进 `routes.identity()`。
2. **`bank_csrf` 的 Path 是 `/api`，页面在 `/` 读不到 → 刷新后所有写操作 403。** 这条只有
   真浏览器能发现，是本批次最大的收获。
3. `test_bill_upload.py::second_session()` 还造 P1 之前的会话行。
4. `test_conversation_serial_migration.py::_insert_user()` 在 `0019` 删 `display_name` 时被
   连带删掉了这一列，但该用例回到 `0010` 造数据，那里它还是 NOT NULL → 全量跑才暴露。
5. 外加文档：`README.md` 的本机库还写着系统 PostgreSQL 5432（实际是容器 55432）、
   `_accept/demo-script.md` 的自检命令在 P2 之后全部 401。

第 4 条说明一件事：**「跑改动附近的用例」这个策略不够。** 这个文件跟 P1 的改动没有任何业务
交集，它只是因为共享了 `app_user` 这张表而失效。

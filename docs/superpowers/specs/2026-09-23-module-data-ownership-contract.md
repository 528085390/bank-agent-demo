# 功能模块数据归属与持久化契约

> 版本：v1｜日期：2026-09-23｜读者：Agent 底座、领域模块与 `bank_backend` 开发者
>
> 本文定义数据归属、持久化边界和迁移协作规则。模块工具/API 的输入输出仍以[模块工具契约](2026-09-22-module-tool-contract-v1.md)和[模块接入契约](2026-09-22-module-integration-seam-contract.md)为准。

## 1. 目标与适用范围

本契约解决三个问题：一份数据由谁负责、其他模块如何使用它、数据库结构由谁变更。它不预先设计所有模块的表；每个模块在确定持久化需求时提交数据声明，由数据所有者和平台负责人确认后再实现。

本文适用于同一 Agent 服务中的领域模块、Agent 平台基础设施，以及独立部署的模拟银行服务 `bank_backend`。这里的领域 Agent 是应用内模块，不等同于独立部署服务。

## 2. 基本术语

| 术语 | 定义 |
| --- | --- |
| 服务 | 独立部署、独立发布并通过 API 或消息与其他服务交互的运行单元，例如 Agent 后端或 `bank_backend` |
| 模块 | 服务内具有明确业务职责的代码边界，例如账单、转账、通知或用户偏好 |
| 数据所有者 | 对数据含义、正确性、生命周期、授权读写和迁移负责的唯一模块或服务 |
| 权威数据源 | 对某项事实拥有最终解释权的存储；其他副本只能是缓存、投影或有时限的快照 |
| 共享平台数据 | 多个模块需要引用、但由平台基础设施单独负责的数据，例如稳定的 `user_id` |

## 3. 总体架构规则

1. **数据库边界按可独立部署的服务划分，不按 Agent 或功能模块数量划分。** Agent 服务内的多个模块共用 Agent 服务的 PostgreSQL 数据库连接和迁移体系；每个模块只拥有自己声明并获准的表。`bank_backend` 作为独立服务拥有自己的数据库和迁移链。
2. **共用数据库不代表共享表所有权。** 每张业务表只有一个所有者。其他模块通过所有者提供的 Python 服务接口、工具/API 或明确的只读查询接口使用数据，不直接写入或依赖对方的 ORM 模型。
3. **一个业务事实只有一个权威数据源。** 不在 Agent 数据库中复制银行余额、交易或订单作为第二份真相。确需保存的展示快照必须声明用途、来源、生成时间和刷新/失效规则。
4. **公共模型保持最小。** `user_id`、请求关联标识等由平台统一定义；不创建让所有模块随意添加字段的万能用户表、万能任务表或万能 JSON 表。
5. **PostgreSQL 是关系业务数据的持久化来源。** Redis 可承载队列、短期缓存或临时协调信息，不作为账户、订单、联系人、偏好等业务事实的唯一存储。

开发、测试和生产可使用同一 PostgreSQL 集群，但必须使用明确的数据库或 schema 隔离，并使用各自凭据和权限。当前测试会创建随机 schema 隔离用例；测试不得迁移、清理或写入开发/生产 schema。不同服务不得共用生产数据库角色。

## 4. 当前项目的数据归属基线

| 数据类别 | 权威所有者 | 归属规则 |
| --- | --- | --- |
| Agent 登录会话、身份映射、LangGraph checkpoint | Agent 平台 | checkpoint 属于对话恢复基础设施，不归任何领域 Agent 所有；模型密钥按现有安全设计留在运行时，不因本契约而改为落库 |
| Agent 产品的用户身份 | Agent 平台 | Agent 的 `user_id` 是 Agent 产品内的稳定标识；它不等于银行客户主数据，也不自动授予银行账户访问权 |
| 模拟银行客户记录 | `bank_backend` | `bank_backend.users` 是模拟银行自己的客户记录，主键是银行侧客户号（演示数据当前为 `u_wealth`，2026-09-23 时为 `u_zhang`，见 §4.0 的更新注）。Agent 侧用户（`user_0001`）与它的对应关系是**显式且完整**的：`AppUser.bank_customer_id` 一列存的就是银行客户号，`Identity.bank_customer_id(user_id)` 读它，运行时注入 `TrustedContext.bank_customer_id`。**两侧 ID 字符串并不相同，也不是靠"名字一样"关联的**——见下方 §4.0 |
| Agent 用户交互偏好 | Agent 平台的用户偏好模块 | 语言、回复风格、界面习惯等 Agent 产品偏好不属于银行核心数据；通知投递偏好可由通知模块拥有，须在数据声明中明确唯一所有者 |
| 用户私人联系人及关系信息 | Agent 联系人/个人记忆模块 | 用户告诉 Agent 的联系人姓名、关系、生日和提醒偏好属于用户的 Agent 资料；由 Agent 侧保存并管理生命周期 |
| 银行客户、账户、余额、交易、订单、订阅等银行业务事实 | `bank_backend` | Agent 通过银行 API 读取或发起操作；Agent 不直连银行业务表 |
| 银行侧收款人/受益人及账户验证状态 | `bank_backend` | 仅当该数据代表银行认可、可用于银行操作的收款账户时归银行服务负责 |
| 已确认的定时转账、扣款、生日订单等资金操作 | `bank_backend` | 任务状态、到期执行、资金变更和最终结果由能够原子修改银行业务事实的服务负责 |
| 不会产生银行交易的提醒、Agent 后续跟进和通知投递 | Agent 通知模块 | Agent 负责提醒计划与投递状态；投递邮件/消息不改变银行订单或余额 |
| 模块私有的解析进度、分类规则或领域配置 | 对应功能模块 | 只有在跨请求恢复或产品需求确实需要时才持久化；模块自行定义并维护表 |

Agent 平台提供稳定的 `user_id`。其他服务可保存该标识作为外部引用，但服务数据库之间不建立跨库外键；身份验证和用户归属必须由 API/可信调用上下文确认，不能信任模型生成的身份字段。

### 4.0 演示环境的身份映射是显式的，不是"同名巧合"

**Agent 侧用户与银行侧客户是两个不同的标识，靠一列外键关联**：

| | 标识 | 来源 |
| --- | --- | --- |
| Agent 侧用户 | **`user_0001`** | `AppUser.user_id`（`app/storage/seed.py` 的演示种子） |
| 银行侧客户 | **`u_wealth`** | `bank_backend.users.id`（`bank_backend/app/storage/wealth_seed.py` 的 `WEALTH_USER`；2026-09-23 时用的是 `bank_backend/app/storage/seed.py` 的 `DEFAULT_USER_ID` = `u_zhang`） |
| 两者的映射 | `user_0001` **→** `u_wealth` | **`AppUser.bank_customer_id` 列**（迁移 `0006_bank_customer_id`） |

> **2026-10-11 更新**：演示种子的绑定改为 `u_wealth`（`backend/app/storage/seed.py` 的 `DEMO_BANK_CUSTOMER`，2026-10-11 单独提交）。理由是接入底座运行时的领域目前只有理财，而理财的银行调用需要样例持仓、两个活期账户与有效风险测评，这些都在 `u_wealth` 名下；`u_zhang` 同时是 `bank_backend` 自己的默认客户，正是所有银行工具 fail-closed 要躲开的那个回退。**映射机制一个字没变**——仍然是 `AppUser.bank_customer_id` 一列、`Identity.bank_customer_id` 解析、`TrustedContext.bank_customer_id` 注入；`u_zhang` 仍然出现在别处，但那是 `bank_backend` 自己的默认客户，不是演示用户的绑定。

读取路径只有一条，且是**可信的**（不经过模型）：

```text
AgentRuntime(customer_resolver=Identity.bank_customer_id)
  → Identity.bank_customer_id("user_0001") = SELECT AppUser.bank_customer_id WHERE user_id='user_0001'
  → TrustedContext.bank_customer_id = "u_wealth"
  → BankClient 把它作为 bank_backend 的 user_id 参数发出
```

**所以映射是"显式且完整"的**：演示数据里这一列有值（`u_wealth`），
不是靠两个 ID 恰好拼写相同来关联——它们**并不相同**。
种子脚本还会对被重新播种前就存在、`bank_customer_id` 为 `None` 的用户**补齐**这个绑定。

**绑定缺失时是 `None`，此时工具必须失败关闭**（接缝契约 §4.1.3）：
`bank_backend` 把 `user_id` 当**可选**参数，缺了它会用自己的默认客户回答，
那是跨客户读数据，而且是 HTTP 200。所以"没有绑定"绝不能被当成"用默认客户"。

> **这不等于认证或授权。** 这一列是**演示级的归属声明**，不是凭据：
> 它不证明调用方是谁，`bank_backend` 也不据此做资源级授权（首版只做基础存在检查）。
> 生产式身份映射仍须由可信服务端上下文确认（§3、§10）。

### 4.1 联系人与收款人的区分

“联系人”不是单一数据类别：

- 用户维护的关系信息（姓名、关系、生日、提醒偏好）属于 Agent 联系人数据。
- 银行确认并用于资金操作的收款账户资料属于银行受益人数据。
- Agent 发起转账时只传递完成该次业务所需的收款账户引用或经用户确认的收款信息，由 `bank_backend` 校验并执行。不得为了方便把完整银行账户资料复制到 Agent 长期记忆中。

现有 `bank_backend.contacts` 同时包含联系人姓名、生日和收款账户关联，并被生日订单流程使用。这是当前模拟系统的既有实现，属于个人联系人与银行受益人边界合并的历史简化。新功能按上面的归属规则设计；拆分或迁移既有数据时必须单独说明映射、兼容期、回滚和数据保留策略，不能静默改变现有 API 语义。

### 4.2 定时任务的区分

判断任务所有者看任务的**效果**，而不是由谁接收用户的自然语言：

- “提醒我下周给联系人打电话”由 Agent 通知模块保存和触发。
- “下周三从账户 A 向收款人 B 转账”在银行服务接受并确认后，由 `bank_backend` 保存并执行。Agent 可保存用户交互/提醒状态，但不能成为转账执行状态的权威来源。
- 一项提醒到期后若要执行资金操作，必须经过已确认的银行操作接口；不得让 Agent 通知 worker 直接更新银行数据库。

## 5. 模块开工前的数据声明

凡模块需要新增持久化数据，须在实现数据库写入前提交以下声明。纯计算且不跨请求保留的临时值无需建表，但应说明它只存在于请求或 LangGraph checkpoint 状态中。

```markdown
### 数据声明：<module-id>
- 功能/场景：
- 数据实体与字段草案：
- 为什么需要持久化、保留多久：
- 权威数据源与唯一所有者：
- 存储服务/数据库：
- 读者和写者：
- 跨模块/跨服务依赖及调用接口：
- 是否包含个人信息、金融信息、凭证或模型输出：
- 用户删除、任务取消和数据过期时的处理：
- 唯一性、状态约束、事务边界和幂等要求：
- 预期查询方式与索引：
- 迁移、兼容和测试隔离方式：
```

数据声明保存在对应模块的契约或设计文档中，不把所有模块的草案堆进一个共享文件。模块现有工具契约可作为入口；跨模块的数据归属索引和已裁决的公共规则集中维护在本文第 4 节及下表。平台负责人确认归属后，模块契约应链接到本文件，并记录其数据声明。

## 6. 数据库与迁移规则

1. PostgreSQL 表结构通过项目对应的 Alembic 迁移维护。运行中的应用只连接并使用已部署的结构，不在请求处理或普通应用启动时自行升级数据库。
2. Agent 服务和 `bank_backend` 保持各自独立的 Alembic 配置、版本表和迁移链。一个服务的迁移不得连接另一个服务的生产数据库。
3. 同一服务内每个模块只修改自己拥有的表。新增/修改公共表、修改其他模块表或改变共享标识语义，必须先由相关所有者评审，并在变更说明中列出消费者和兼容策略。
4. 迁移提交前检查空库安装、已有库升级、约束/索引和必要的回填；破坏性变更采用“先兼容、再迁移、最后清理”的分阶段过程。未经确认不得删除或重写用户数据。
5. 种子数据与生产迁移分开管理；开发/测试重置逻辑不得连接生产库。测试通过独立测试数据库或随机 schema 执行，不复用公共测试表进行破坏性清理。
6. 表、列、索引和唯一约束应表达可由数据库保证的不变量。金额使用整数最小货币单位或项目已确定的精确数值类型；时间保存时区信息。JSONB 用于确实需要演进的非核心结构，不代替可查询、可约束的关系字段。

## 7. 事务、幂等与跨服务调用

- 一个服务拥有的数据变更在该服务的事务内完成，并由该服务检查所有业务不变量。
- 重试可能重复产生副作用的写 API 必须定义幂等键范围、请求指纹、有效期和重复请求响应；同一逻辑调用重试必须复用同一幂等键。
- 不使用跨数据库事务或跨服务外键。涉及多个服务的流程通过幂等 API 和明确的状态机协调；当需要可靠发布事件时，由后续方案引入 transactional outbox。需要补偿的步骤必须在工具契约中说明。
- 模块间查询也应走所有者定义的接口，避免把“只读 SQL”变成长期的跨模块表依赖。

## 8. 数据安全与生命周期

每项个人信息、金融信息和凭证都要有明确用途、最小采集范围、读写角色、保留期限和删除/匿名化策略。密码、验证码、访问令牌、模型 API Key 等认证秘密不得因“方便恢复”而写入业务表、审计详情或普通日志。审计记录应记录可追溯的事件和业务引用，不复制不必要的原始敏感载荷。

用户注销、联系人删除、模块卸载、任务取消和保留期到期时，数据所有者负责执行删除、匿名化或依法保留，并说明会影响的下游快照、任务和审计记录。调用方不得自行猜测其他所有者的数据保留策略。

## 9. 评审与契约变更

涉及数据所有权、权威来源、服务边界、跨模块读写、公共身份标识或保留策略的变化属于契约变更。变更说明至少包括：

1. 原因与新旧归属。
2. 受影响表、API、模块及消费者。
3. 数据迁移、兼容窗口、回滚与数据保留方式。
4. 验证方式，包括迁移测试、幂等/事务测试和敏感数据检查。

模块可独立推进自己边界内的实现，不要求所有模块同时完成数据设计；但不得以“最后融合”为由先创建重复权威数据或未评审的跨模块表依赖。

## 10. 当前落实状态

- Agent 服务已使用 PostgreSQL、SQLAlchemy 和 Alembic；LangGraph checkpoint 表由独立部署命令初始化，应用启动只检查其存在。
- `bank_backend` 有自己的 PostgreSQL 配置、模型和 Alembic 迁移链，通过 API 提供模拟银行业务。
- 当前领域 Agent 工具仍处于逐步接入阶段，尚不能据此推断每个领域模块都需要自己的持久化表。
- 当前 Agent 联系人/偏好存储与通知调度尚未形成本文描述的完整模块实现；新增时应先提交第 5 节数据声明。
- 当前两个项目的集成测试连接同一 PostgreSQL `test` 数据库，但 Agent 后端与 `bank_backend` 各自创建带不同前缀的随机 schema 运行迁移；测试清理只删除各自 fixture 创建的 schema。
- 当前仓库的开发/测试凭据也有共享配置。第 3 节关于按服务/环境分配数据库角色与权限是目标要求，尚未完全落实；部署权限调整应单独安排，不能把文档目标误读为现状。
- 当前身份仍是演示级：Agent 使用演示会话/用户（`user_0001`），`bank_backend` 也有自己的模拟客户记录（`u_zhang`）；**两者的映射是显式的**（`AppUser.bank_customer_id`，见 §4.0），但它**不构成认证或授权**。保存真实用户联系人或偏好前，必须先定义可信身份映射和服务间身份传递。

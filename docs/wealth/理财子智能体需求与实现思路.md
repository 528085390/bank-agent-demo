# 理财子智能体需求与实现思路

> 修订日期：2026-10-06。面向负责理财子智能体开发的同学。  
> 本次纠正：**假数据不等于内存返回。银行后端需要真实 HTTP 接口、业务处理和数据库持久化，只是数据来源和金融规则采用简化模拟。**  
> 架构仍采用已确认的 B 方案：理财子智能体拥有自己的内部多步骤工作流，不承担前端和主智能体接入。  
> 本轮仅修订文档，未实现下文新增接口、迁移或智能体代码。配套文档：[理财子智能体从零到实现计划](理财子智能体从零到实现计划.md)（同目录）。

## 一、先把边界讲清楚

### 1.1 正确的目标

做一个可以独立调用的理财子智能体，能够完成产品查询、风险测评、推荐对比、申购、持仓收益查询和赎回。它通过 HTTP 调用项目里的模拟银行后端，银行后端查询或修改 PostgreSQL 中的模拟业务数据。

```text
独立调用程序／本地对话入口
           ↓
理财子智能体：理解、追问、多步工具调用、确认、模拟验证
           ↓ HTTP
现有 bank_backend：接口校验、简化业务规则、数据库事务
           ↓
PostgreSQL：产品、账户、测评、持仓、订单、流水、审计、幂等结果
```

**“独立”是不依赖前端和主智能体，不是不依赖银行服务和数据库。** 完整运行和最终验收必须启动模拟银行服务并连接指定数据库。

### 1.2 什么是真的，什么是模拟的

| 项目 | 本次要求 |
| --- | --- |
| 银行产品、用户、账户资金 | 模拟数据，使用种子写入数据库 |
| 理财收益、风险问卷、到账时间 | 简化演示规则，不接真实市场、银行、短信或支付系统 |
| HTTP 接口 | 真实实现，能独立请求，有参数校验和明确结果 |
| 查询 | 从数据库读取，而不是每次返回函数里写死的字典 |
| 申购、赎回 | 真正修改模拟账户与持仓，提交订单、流水等记录到数据库 |
| 风险测评 | 答案和评分结果需要落库，重启后仍可读取 |
| 交易核实 | 从已保存订单及幂等记录查询结果，不凭聊天内容判断成功 |
| 服务重启 | 不清空业务数据；只有开发者显式初始化／重置才改变演示数据集 |
| 测试替身 | 允许在 Agent 单元测试中使用，但不能代替 HTTP＋数据库主路径和最终验收 |

### 1.3 相比上一版，明确替换哪些决定

- 删除“正式实现使用进程内 `MockWealthBank`”的方案，改为 **`HttpWealthBank` 适配现有银行 HTTP 服务**。
- 删除“不需要银行 HTTP 服务和数据库即可完成验收”的结论。
- 删除“测评、余额、持仓和交易只存内存，重启恢复种子”的业务存储方案。
- **实施第一阶段就是补齐银行接口及持久化能力。** 已有接口复用并补必要校验，缺失接口新增，不把所有接口重写一遍。
- 推荐排序、对话、追问和多步工作流仍是智能体重点；银行后端不做复杂金融平台，只做支撑功能闭环的简单完整实现。
- 会话草稿、未确认意图等临时状态首版仍可放 Agent 内存，但不得作为余额、风险等级或成交记录的权威来源。

## 二、理财智能体需要实现什么

### 2.1 功能清单

| 功能 | 智能体负责什么 | 银行后端负责什么 |
| --- | --- | --- |
| 产品查询 | 听懂筛选条件，解释产品参数 | 查询 products 并返回事实 |
| 风险测评 | 对话收集五题答案，澄清含糊回答 | 规则评分，保存答案、等级、有效期，提供查询 |
| 产品推荐 | 结合资金、用钱时间、流动性和有效测评，筛选并解释候选 | 提供产品与测评数据，申购时复核硬约束 |
| 产品对比 | 对齐风险、期限、起购额、赎回条件和模拟收益参数 | 提供产品详情；已有对比接口可参考，但非额外必需接口 |
| 申购 | 补字段、生成预览、取得确认、收集模拟验证码、执行并核实 | 校验、扣减模拟余额、新增持仓、订单、流水、审计、幂等记录并提交 |
| 持仓与收益查询 | 解释本金、当前价值、持有收益、已实现收益 | 查询已存持仓及赎回订单，返回数值 |
| 赎回 | 明确持仓和金额、确认与模拟验证、核实到账 | 减少持仓、增加账户余额，保存订单、流水、审计和幂等记录 |
| 取消、改参、异常 | 失效旧确认、停止未提交操作、处理未知结果 | 拒绝非法请求，从持久化记录核实已提交交易 |

赛题明确要求“产品推荐与对比、风险评估、一键申购／赎回”；理财收益查询为只读查询，理财申购属于红色强验证操作，不能按金额小而免验证。[S1]

固定演示验证码只能演示验证流程，不等于真实多因子认证。赎回也采用确认＋模拟验证，是本项目统一选择，不宣称赛题对赎回逐项作了相同规定。

### 2.2 三条主流程

**推荐：** 理解需求 → 补齐金额、用钱时间、流动性 → 查银行测评 → 没有有效测评就问卷并保存 → 查产品 → 规则筛选 → 推荐／对比。

**申购：** 确定产品、金额、本人付款账户 → 查产品、账户和测评 → 预检 → 展示预览 → 用户确认 → 模拟验证 → 调银行申购 → 银行事务提交 → 查回执／订单核实 → 回答。

**赎回：** 查本人持仓 → 明确部分／全部赎回、金额、本人到账账户 → 校验可赎回 → 展示预览 → 确认与模拟验证 → 调银行赎回 → 银行事务提交 → 核实订单与持仓 → 回答。

“一键”不等于省去确认和验证；只是由智能体把原本多层菜单和操作串起来。

### 2.3 不做哪些扩展

不做前端、Supervisor 接入、真实银行连接、行情预测、真实短信、人脸识别、复杂净值份额系统、分布式资金平台、到期调度和其他领域智能体。**但本模块需要的 HTTP、数据库迁移、业务落库、基础事务与幂等属于本次任务，不能以“不做复杂银行”为由省略。**

## 四、银行接口契约：需要查什么、写什么

### 4.1 优先新增的四个接口

以下路径为**拟新增设计**，不是现有路由。

| 拟新增接口 | 请求重点 | 返回重点 | 数据库处理 |
| --- | --- | --- | --- |
| `POST /api/wealth/risk-assessments` | user_id、五题标准答案 | assessment_id、score、risk_level、rule_version、assessed_at、expires_at、valid | 服务端评分并新增测评记录；记录必要审计 |
| `GET /api/wealth/risk-assessments/latest` | user_id | 本人最近测评和基于银行模拟时钟计算的 valid；没有记录返回空结果 | 查询测评表，不写库 |
| `GET /api/wealth/orders/{order_id}` | user_id、order_id | 本人理财订单、产品／持仓、金额、状态、账户、transaction_id、执行结果 | 查询已有 orders，仅允许理财订单类型 |
| `GET /api/wealth/orders/by-idempotency-key` | user_id、operation_type、idempotent_key | found、原执行回执、order_id；没有记录为 found=false | 按三元组查 idempotency_records，再核实关联理财订单 |

静态路径 `by-idempotency-key` 必须先于动态 `{order_id}` 注册，避免误把静态段当作订单 ID。operation_type 只允许现有 `purchase_product`／`redeem_product`，不能借接口查询其他域结果。

继续使用银行既有 `{code, message, data}` 响应封装。按幂等键暂时查不到结果，不足以证明在途请求没有提交；Agent 对此前写超时仍返回 unknown，而不是“失败且未扣款”。

不额外新增验证服务、推荐引擎和收益结算系统。用户提交验证码时随申购／赎回请求送达银行，由银行校验配置的演示码；不必另做短信发送接口。

### 4.2 已有写接口的入参和权威边界

**申购请求：** `product_id`、`from_account_id`、`amount_minor`；user_id、confirm、mfa_code 和幂等键由可信运行时装配。已有 term_months 不允许用户任意缩短产品期限，首版缺省使用产品期限，显式传入时必须与产品一致。

**赎回请求：** `holding_id`、`amount_minor`、`to_account_id`；其余可信字段同上。Agent 展示并确认到账账户后再提交，不把服务端缺省账户当成用户已经授权。

**不可由模型决定的值：** 银行客户身份、confirmed、verified、验证码、幂等键、账户余额、最终风险评分和成交状态。

模型可以提取业务槽位，但只有运行时经过当前待办确认后，才能设置 `confirm=true` 并提交验证码。银行仍要重新检查硬规则，不能相信 Agent 说“我检查过了”。

### 4.3 查询使用现有字段，不另造一套金融模型

| 数据 | 采用／新增字段 | 说明 |
| --- | --- | --- |
| 产品 | 复用 `min_amount_minor`、`max_amount_minor`、`expected_return`、`risk_level`、`duration_months`、`status`；新增 `redeem_rule` | 继续 low／medium／high，available／sold_out；不另造 min_purchase_minor 或 term_days 列 |
| 账户 | 复用 `balance_minor`、user_id、account_type、status | 首版没有复杂冻结资金体系，可用余额按现有余额处理 |
| 持仓 | 复用 `principal_minor`、`current_value_minor`、`accrued_interest_minor`、maturity_date；新增响应字段 `redeemable_minor`、`realized_income_minor` | 可赎回额派生计算；已实现收益汇总完成赎回订单，不必新增持仓收益账本 |
| 订单 | 复用 order_id、order_type、holding_id、amount_minor、status、details、transaction_id | `order_id` 是业务订单；`transaction_id` 是资金流水，不混用 |
| 测评 | 新增 assessment_id、user_id、answers、score、risk_level、rule_version、assessed_at、expires_at | answers 用结构化字段保存，等级由银行计算，不接受模型直接指定 |

模拟收益率必须解释为演示参数，不能当作真实收益预测或保证收益。金额统一整数分；金额比较、评分和本金分摊由程序处理。

## 五、数据库怎么落，简单但完整

### 5.1 最小表变更

1. **新增 `wealth_risk_assessments` 表**：用户外键、答案、分数、等级、规则版本、测评／过期时间；按用户和测评时间索引，保留历史测评。
2. **给 products 新增 `redeem_rule`**：仅 `flexible`／`maturity_only` 两种。旧产品按 duration_months 回填：0 为 flexible，正数为 maturity_only，之后明确存储该字段。
3. 账户、持仓、订单、资金流水、审计、幂等表全部复用。收益可用查询派生，不因展示一个数就再建一个子系统。
4. 在现有迁移链后新增迁移，不回改已经使用的首版迁移；迁移需要支持已有数据升级。
5. 测评新增用户外键后，现有开发者重置逻辑需在删除 users 之前删除测评记录。不能只加表而忘记 seed/reset 的依赖顺序。

### 5.2 一次申购需要落哪些数据

```text
读取并锁定本次涉及资源／同用户理财写入口
→ 查幂等记录，已有同键同业务参数则返回原回执
→ 检查本人账户、产品、测评、风险、金额、确认和模拟验证码
→ accounts 减少余额
→ holdings 新增一笔持仓
→ orders 新增 product_purchase 订单
→ transactions 新增扣款流水
→ audit_logs 写执行记录
→ idempotency_records 保存请求业务指纹和回执
→ 同一数据库事务提交
```

失败时资金、持仓、订单等业务修改整体回滚；失败审计可以沿用现有独立事务记录，不得把“有失败审计”误判为“资金没有回滚”。

### 5.3 一次赎回需要落哪些数据

同一事务内检查本人持仓、可赎回额和本人到账账户，减少持仓价值及本金、增加账户余额，保存 product_redeem 订单、入账流水、审计和幂等结果。全部赎回后持仓标记 redeemed 并保留记录，不直接删除。

部分赎回采用固定整数规则：赎回前本金 P、价值 V、赎回金额 R，部分释放本金为 floor(P×R/V)；全部赎回释放所有剩余本金。本次实现收益为 R 减释放本金，存入现有赎回订单 details。这样不需要复杂份额系统，也不会用浮点推导资金。

### 5.4 持久化与幂等的最小可靠性

- 幂等键沿用现有 `(user_id, operation_type, idempotent_key)`；同键同业务参数返回原回执，同键不同产品／持仓／账户／金额／期限必须拒绝。
- 业务指纹不包含验证码等秘密；不要把 mfa_code 保存到幂等结果或审计。
- 幂等查询需要在余额、持仓等随首笔交易改变的校验前处理，否则首笔全部赎回后重试会错误地变成“已赎回，失败”。
- 只在资金已变更后捕获幂等插入唯一键冲突，不足以保证并发不重复扣款。理财写入口需在同一事务里先串行化同用户写操作、查询并比较幂等键，再执行；同时锁定涉及账户／持仓。限定在理财范围，不建设分布式协调服务。
- 银行重启不能重建种子或丢失幂等记录；重启后同键请求仍返回原订单。
- Agent 会话可不持久化，但它重启不能把聊天中的“已确认”当作新授权，也不能凭丢失的本地状态判断银行未成交。

## 六、B 方案下的智能体实现思路

### 6.1 模块结构

`wealth`是一个独立业务模块，但内部按职责拆包，不能把运行时、工作流、规则、银行适配器和模型提示全部放在同一层：

```text
backend/app/modules/wealth/
├── contracts/       # 请求、响应、银行协议和DTO
├── application/     # 对外Agent运行时与依赖装配
├── workflow/        # 状态、图、节点和多步骤推进
├── domain/          # 推荐、对比、金额和交易预检规则
├── infrastructure/  # HttpWealthBank与只读工具
├── llm/             # prompts与结构化决策解析
├── cli.py
└── README.md
```

依赖方向为：`application → workflow/domain/infrastructure/llm → contracts`。领域规则不直接访问银行，模型解析不直接执行资金写操作，所有申购／赎回仍由运行时的受控节点调用`infrastructure`中的银行适配器。

```text
WealthAgent.handle(context, request)
    ├─ application/runtime：校验身份、恢复待办、确认与结果核实
    ├─ workflow：理解 → 补信息 → 查询 → 判断 → 输出／等待
    ├─ llm：自然语言理解、结构化决策、表达
    ├─ domain：推荐筛选、意图规范化、交易预检
    ├─ infrastructure：只读工具与HttpWealthBank
    └─ 现有 BankClient → bank_backend → PostgreSQL
```
### 6.1.1 不能重复造轮子：复用项目公共能力

上面的分包只表示理财领域自己的代码边界，不表示重新定义一套工具协议、身份协议或模型客户端。现有项目已经提供了公共基础，理财模块应当依赖并实现这些公共接口：

| 现有公共能力 | 位置 | 理财模块的使用方式 |
| --- | --- | --- |
| 模块声明、工具注册和处理器绑定 | `backend/app/modules/base.py` | 在 `wealth/__init__.py` 组装 `ModuleSpec`；理财只提供自己的工具规格和处理器 |
| 工具协议、参数Schema、读写副作用、统一错误码、可信身份 | `backend/app/tools/protocol.py` | 直接使用 `ToolSpec`、`ToolInvocation`、`ToolResult`、`TrustedContext`、`ErrorCode`，不重新定义同名类型 |
| 工具权限、参数校验、身份注入、审计边界 | `backend/app/tools/gateway.py`、`backend/app/tools/handle.py` | 通过 `ToolGateway`／`AgentToolHandle` 调用工具；模型不能自行指定银行客户号、幂等键或确认字段 |
| 模块发现、工具目录和Agent绑定 | `backend/app/modules/registry.py`、`backend/app/modules/__init__.py` | 让 `wealth.MODULE` 进入现有注册表；不在理财模块里维护第二套全局注册表 |
| Agent声明、字段元数据、通用状态和运行时 | `backend/app/agents/declaration.py`、`backend/app/agents/state.py`、`backend/app/agents/runtime.py` | 复用通用身份、会话、事件、检查点和锁；只在 `wealth` 增加理财待办、申购／赎回意图等领域状态 |
| 银行HTTP客户端 | `backend/app/integration/bank_client.py` | `infrastructure/bank_adapter.py` 复用 `BankClient`，只负责把理财业务方法映射到银行接口 |
| 模型客户端 | `backend/app/integration/model_client.py` | `llm`层接收现有 `ModelClient`，不自行创建另一套OpenAI／HTTP客户端 |
| 审计和公共错误处理 | `backend/app/audit/`、`backend/app/modules/base.py` | 使用现有审计入口和 `ToolData`／`ToolFailure` 结果约定 |

因此，理财模块自己定义的是**理财领域内容**：产品筛选规则、风险测评流程、申购／赎回意图、待确认状态、领域提示词，以及产品／账户／持仓工具的具体参数和处理逻辑；公共的工具外壳、身份注入、权限校验、错误语义、审计和HTTP／模型客户端全部复用现有实现。

工具注册的关系应当是：

```text
wealth/infrastructure/tools.py
    ├─ 定义理财工具的 ToolSpec 与 handler
    └─ 使用 app.tools.protocol 的公共类型
              ↓
wealth/__init__.py
    └─ 组装 ModuleSpec(name="wealth", declaration=WEALTH, tools=..., handlers=...)
              ↓
app.modules.registry.build_registry()
              ↓
ToolGateway / AgentToolHandle
```

`WealthAgent` 可以拥有自己的内部B方案工作流，但它不是另起炉灶：工作流复用公共 `TrustedContext`、`ModelClient`、`BankClient`、`AgentRuntime` 能力；只有理财特有的节点和状态放在 `wealth` 包内。
### 6.2 独立调用契约

- `build_wealth_agent(model, bank, clock) -> WealthAgent`；正式 bank 必须为 HTTP 适配器。
- `WealthAgent.handle(context: TrustedContext, request: WealthRequest) -> WealthResponse`。
- request.kind：message／answer／confirm／verify／cancel；配合 text、pending_id、verification_code。
- response：status、summary、facts、business_ids、pending、error_code、trace_id。
- status：completed／waiting_input／waiting_confirmation／waiting_verification／cancelled／failed／unknown。

只读工具可以由模型选择；保存测评由明确完成问卷的流程调用，是非资金写操作，需要审计但不需要交易验证码。申购／赎回只能由运行时写节点调用，不能出现在模型可自由执行的工具白名单里。

验证码只走独立 verify 输入与 HTTP 写请求，不进入模型上下文和日志。银行验证码错误不改变余额；Agent 保留待办供有限次数重试。写请求超时与“验证码明确错误”必须区别处理，前者先核实订单，不盲重试。

### 6.3 HTTP 适配器的方法

| 方法 | 对应银行请求 |
| --- | --- |
| `list_products(context, filters)` | 产品列表 |
| `get_product(context, product_id)` | 产品详情 |
| `list_accounts(context)` | 本人账户 |
| `list_holdings(context)`、`get_holding(context, holding_id)` | 本人持仓 |
| `get_risk_profile(context)` | 最近测评查询 |
| `submit_risk_assessment(context, answers)` | 提交问卷并保存银行评分 |
| `purchase(context, intent, verification_code, idempotency_key)` | 申购；运行时内部专用 |
| `redeem(context, intent, verification_code, idempotency_key)` | 赎回；运行时内部专用 |
| `get_order(context, order_id)` | 本人理财订单 |
| `find_order_by_key(context, operation_type, idempotency_key)` | 根据幂等键核实；运行时内部专用 |

适配器不保存余额、持仓和交易副本，也不直接连接银行数据库。直接 SQL 只供银行侧实现和测试核验，不能变成 Agent 绕开 HTTP 的正式路径。

### 6.4 运行状态与存储归属

| 数据 | 权威存储 | 首版重启行为 |
| --- | --- | --- |
| 产品、账户、持仓、订单、流水 | 银行 PostgreSQL | 保留 |
| 风险测评、已实现收益来源、幂等结果、银行审计 | 银行 PostgreSQL | 保留 |
| 会话槽位、最近候选顺序、未提交待办、Agent内部计数 | Agent 内存 | 可丢失；重新澄清和确认 |
| 未知结果的订单号／幂等键 | 原调用结果或调用方留存的请求标识，用于银行查询 | 不能仅靠丢失的会话恢复；应保留核实引用，不自动重发 |
| 演示产品种子 | 显式初始化写入银行数据库 | 不随服务重启执行 |

测评有效性与产品到期判断以银行模拟业务时钟为准；Agent 待办 5 分钟有效期由注入运行时钟控制。这两个时钟用途不同，不能用本机日期覆盖银行已返回的 valid 或 redeemable_minor。

## 七、业务规则与必要保护

### 7.1 简单风险问卷

五题，每题0／1／2分：本金损失接受度、投资经验、收入稳定性、投资期限、短期用钱需求。总分0–3为low，4–7为medium，8–10为high；首题“不能接受本金损失”强制等级上限low。有效期30天，以银行业务时钟生成与判断。

问卷由 Agent 引导，评分规则以银行服务为唯一权威实现。Agent 不另建一套评分函数和内存 RiskProfileStore。模型提交“risk_level=high”不能直接修改等级。

### 7.2 推荐与对比

先过滤停售、风险超限、起购不足／超过单笔上限、期限不符和流动性不符。推荐最多三个，按风险较低、期限较短、产品ID稳定排序，不单纯追求年化参数最大。

对比包括风险、期限、起购额、赎回规则、模拟收益参数和适配原因；没有测评时可以客观对比，但不作“适合你”的结论。用户表达“三个月内要用”时按产品月期限和银行返回规则保守匹配；含糊时间需要澄清，不能自行将月份固定当作30天。

### 7.3 交易检查

- 申购：本人活跃账户、可售产品、有效测评、风险匹配、金额上下限、余额、确认、模拟验证；Agent 额外保留用户已表达的流动性限制。
- 赎回：本人持仓、本人到账账户、正金额、可赎回金额、确认、模拟验证；不要求为退出持仓重新测风险。
- flexible 产品可部分／全部赎回；maturity_only 只在到期后可赎回，判定由银行执行。
- 模拟到账即时，手续费0；收益查询只读既有价值，不在每次查询时运行 simulate-interest。

### 7.4 确认、异常与审计

- pending 绑定用户、会话、产品／持仓、账户、金额、意图版本，有效期5分钟；改参后原确认与验证失效。
- 重复确认不延长时限、不清零验证失败计数；一个意图只有一个幂等键。
- 验证错误最多3次后由 Agent 锁定该用户当前进程的写操作。银行现有安全状态另有持久化计数和锁定策略，复用并在理财入口实际检查；不把两者误写成同一个阈值或同一种持久化保证。
- 每次 handle 最多8次模型调用、12次工作流推进；结构错误最多纠正1次，同任务连续澄清最多5次，超限停止。
- 用户输入、产品描述和 HTTP 返回中的自由文本均是数据，不能改写门禁。
- 写回执丢失先按原幂等键核实；查不到或核实异常返回 unknown，不能新生成幂等键重下单。
- Agent 记录脱敏决策动作摘要，银行持久化关键业务审计；不记录验证码、API Key或模型私有推理。
- 模拟 user_id 和验证码不是对外生产认证。演示服务限定受控环境，不声称具备真实银行级鉴权。

## 八、演示数据与验收怎么做

### 8.1 演示数据要写入数据库

复用现有种子体系，但为财富验收提供专用数据集，不破坏其他模块已有固定产品和金额断言。建议用新ID增加：

| ID | 虚构名称 | 风险／期限 | 起购额 | 赎回规则 | 模拟年化参数 |
| --- | --- | --- | --- | --- | --- |
| p_demo_cash | 演示灵活理财 | low／0月 | 100元 | flexible | 2% |
| p_demo_stable | 演示稳健理财 | medium／3月 | 1000元 | maturity_only | 3.5% |
| p_demo_growth | 演示进取理财 | high／12月 | 5000元 | maturity_only | 6% |
| p_demo_closed | 演示停售产品 | low／0月 | 100元 | flexible，sold_out | 9% |

专用用户主账户余额20,000元，备用账户用于账户歧义；预置灵活持仓本金1,000元、价值1,005元。初始化须通过可复现的数据准备流程保持账户和流水一致，不直接改余额破坏已有对账规则。重启服务不执行重置。

### 8.2 必须通过的闭环

1. 无有效测评 → 完成问卷 → 数据库有记录 → 重启银行后仍能查到。
2. 主账户20,000元 → 申购灵活产品2,000元 → 余额18,000元、新仓2,000元，并有订单、流水、审计和幂等记录。
3. 重启银行服务 → 查询账户、持仓、订单，结果保持；重放同幂等键不再次扣款。
4. 赎回新仓500元 → 余额18,500元、新仓1,500元，数据库有赎回记录。
5. 全部赎回新仓剩余1,500元 → 主账户回20,000元，新仓清零，原有样例持仓不变。
6. 没确认、验证码错误、越权、超额、锁定期、重复提交、回执丢失均有明确结果，不出现半笔落库和重复扣款。

### 8.3 分层验证，不再把离线测试当完整验收

- Agent 单元测试：允许脚本模型和 HTTP 测试替身，验证对话与门禁，不声称覆盖落库。
- 银行集成测试：专用 PostgreSQL 测试 schema，验证接口、迁移、事务、测评和订单持久化。
- 独立端到端测试：真实 HTTP 银行服务＋测试数据库＋独立 Agent；可以先用脚本模型稳定回归，再用真实模型进行自然语言冒烟。
- 必须验证重连／新服务实例和真实服务进程重启后的数据，不只对同一对象读两遍。

本项目两个后端都有顶层 app 包，联调时分别在各自工程环境运行，不能把两个 app 同时塞进一个解释器路径。测试库需显式配置并验证隔离，不能误用默认共享库或在有其他人数据的环境调用 seed/reset。

## 九、实施先后顺序

1. **先补银行接口与数据库能力**：迁移、测评保存／查询、订单查询、已有申购赎回必要补齐、数据库测试。
2. **再接独立 Agent**：复用 BankClient，构建 HttpWealthBank，先跑通查库产品查询。
3. **实现多轮选品**：追问、测评接口调用、推荐与对比。
4. **实现交易闭环**：预览、确认、模拟验证、HTTP申购、持仓收益、HTTP赎回和核实。
5. **补可靠性与交付**：防注入、幂等、异常、持久化重启验收、真实模型冒烟。

允许在后续场景发现字段缺口时同步补银行接口，但不能把银行落库推到最后，也不能用内存实现交差。详细文件与逐项任务见配套计划。

# 理财子智能体从零到实现计划

> 后续执行者按任务逐项实施，可使用 `executing-plans` 技能控制节奏。本文所有复选框表示待完成工作，不代表本轮已执行。  
> 修订日期：2026-10-06。本版纠正上一版“银行业务只存内存”的理解，**把银行接口和数据库能力补齐放在第一阶段**。

**目标：** 完成可独立调用的理财子智能体，通过真实 HTTP 接口读写项目模拟银行的 PostgreSQL 数据，实现查询、测评、推荐对比、申购、持仓收益和赎回。

**架构：** B方案——WealthAgent拥有内部多步骤工作流；HttpWealthBank复用已有BankClient访问bank_backend；银行后端复用已有表与理财服务，增加缺失接口和最小迁移。模拟的是产品、资金和业务规则，不是“假装提交成功”。

**技术栈：** 沿用两个工程已有Python、LangGraph、Pydantic、FastAPI、SQLAlchemy、Alembic、PostgreSQL及测试依赖，不新建另一套银行服务。具体第三方API在实施时依据本地版本和Context7核实，本计划侧重业务契约与仓库改动。

**需求依据：** [理财子智能体需求与实现思路](理财子智能体需求与实现思路.md)（同目录）。

## 一、全局约束与本次修正

1. **完整主路径必须是：Agent → HTTP银行接口 → PostgreSQL。** 内存字典、脚本回执、HTTP测试替身仅用于单元测试，不能作为正式银行实现。
2. “子智能体独立”只排除前端和主智能体依赖；银行服务和数据库是本次正式运行依赖。
3. 第一步补所需银行接口和数据模型；已有产品、账户、持仓、申购、赎回接口复用，不重复从零建设。
4. 银行数据使用假数据、规则保持简单，但测评、账户变动、持仓、订单、流水、审计与幂等结果需要落库。
5. 银行业务数据重启后保留；初始化／重置只能由开发者在明确的演示或测试环境显式执行，不随服务启动自动清空。
6. 允许后续开发Agent时补接口字段，但不能把关键落库留到最后，也不能让Agent绕过HTTP直接查银行SQL。
7. 保留B方案，不开发前端、不修改Supervisor路由，不建设真实金融认证、净值交易系统或分布式账本。
8. 身份来自TrustedContext.bank_customer_id，缺少绑定立即拒绝；不能回退到银行缺省用户，模型不得传身份、验证码、确认标志或幂等键。
9. 金额使用整数分，零手续费、即时模拟到账。收益查询只读已保存快照；不向模型开放计息、拨钟、重置种子和安全解锁工具。
10. 申购和赎回都必须经过意图预览、用户确认和模拟验证。银行用配置的演示码校验，不再以“任意数字”代表验证通过。
11. 测评评分、过期和到期赎回以银行规则与银行模拟时钟为准；Agent只收集问卷并使用返回结果，不再维护权威RiskProfileStore。
12. 测试先明确数据库与schema隔离；禁止在未确认的共享环境跑reset、迁移降级或全量清理。
13. 两个工程都有顶层app包，应分别在各自环境运行，HTTP集成不把两套app导入同一个解释器。
14. 每项任务遵循：先写业务失败用例→确认预期失败→最小实现→用例通过→回归受影响范围。提交／推送不属于本计划自动授权。

## 三、接口与数据契约先统一

### 3.1 四个优先新增的银行接口

以下路径均为拟新增，继续使用现有 `{code, message, data}` 响应封装。

| 接口 | 请求 | 响应data | 存储与限制 |
| --- | --- | --- | --- |
| `POST /api/wealth/risk-assessments` | user_id、answers：五题编号对应0/1/2选项 | assessment_id、score、risk_level、rule_version、assessed_at、expires_at、valid | 按服务端规则评分后落测评表，拒绝客户端指定最终等级 |
| `GET /api/wealth/risk-assessments/latest` | user_id | 最近测评及valid；无测评为null | 查询本人记录，valid按银行业务时钟派生 |
| `GET /api/wealth/orders/{order_id}` | user_id、order_id | 理财订单、账户、金额、持仓、状态、流水号、执行结果 | 仅本人product_purchase／product_redeem订单 |
| `GET /api/wealth/orders/by-idempotency-key` | user_id、operation_type、idempotent_key | found、order及原回执；不存在found=false | 三元组查现有幂等表，只允许purchase_product／redeem_product |

静态路由在动态路由之前注册。订单号和流水号严格区分；已实现的生日订单查询不是通用理财订单查询，不能直接当作同一个接口。

### 3.2 已有接口补充项

- 产品查询增加redeem_rule，取flexible／maturity_only；保留min_amount_minor、max_amount_minor、duration_months、expected_return、status等字段。
- 持仓查询增加redeemable_minor和realized_income_minor响应字段；复用current_value_minor，不新建另一套market_value列。
- get_holding必须传入并校验user_id，不能只在路由接收后丢弃身份。
- purchase检查有效测评及风险匹配，全部金额强制确认与模拟验证码；term_months省略用产品期限，显式传值必须相同。
- redeem检查持仓和到账账户归属、到期限制和可赎回金额，同样需要确认与模拟验证。
- 申购、赎回保留现有路由和请求头Idempotency-Key；由Agent运行时生成键，不让模型生成。
- 继续使用已有错误码：1004资源不存在、1005状态非法、1006余额不足、1007确认／模拟验证未通过、1012参数错误。Agent预检可给明确原因；只收到银行通用错误时不要凭空编造更细原因。
- 固定验证规则限定理财服务，不全局改变转账等其他域的金额分级策略。

### 3.3 持久化模型

**新增wealth_risk_assessments：** id、user_id外键、answers JSONB、score、risk_level、rule_version、assessed_at、expires_at；增加用户与测评时间索引。每次完成问卷追加一条，不覆盖历史。

**产品新增redeem_rule：** 回填旧数据：duration_months=0为flexible，正数为maturity_only；设置约束和非空要求。

**复用其他表：** accounts保存余额，holdings保存持仓，orders保存申购／赎回业务，transactions保存资金流水，audit_logs保存审计，idempotency_records保存回执和业务指纹。

持有收益=current_value_minor−principal_minor；已实现收益从完成的赎回订单details中的interest_redeemed_minor汇总。查询派生字段不另建收益系统。

### 3.4 Agent契约和HTTP适配器

```text
build_wealth_agent(model: ModelClient, bank: WealthBank, clock: Clock) -> WealthAgent
WealthAgent.handle(context: TrustedContext, request: WealthRequest) -> WealthResponse
```

WealthRequest字段：kind、text、pending_id、verification_code。kind为message／answer／confirm／verify／cancel；verify字段不进入模型输入。

WealthResponse字段：status、summary、facts、business_ids、pending、error_code、trace_id。status为completed／waiting_input／waiting_confirmation／waiting_verification／cancelled／failed／unknown。

正式WealthBank实现为HttpWealthBank，方法固定为：

```text
list_products(context, filters)
get_product(context, product_id)
list_accounts(context)
list_holdings(context)
get_holding(context, holding_id)
get_risk_profile(context)
submit_risk_assessment(context, answers)
purchase(context, intent, verification_code, idempotency_key)
redeem(context, intent, verification_code, idempotency_key)
get_order(context, order_id)
find_order_by_key(context, operation_type, idempotency_key)
```

模型可调用七个只读方法：产品列表、产品详情、账户列表、持仓列表、持仓详情、最近测评、订单详情。保存测评属于非资金写动作，由完成问卷的流程调用；申购／赎回和按键核实由运行时专用节点调用。

### 3.5 模型与程序分工

模型动作限定为call_read、ask_user、submit_risk、recommend、compare、prepare_purchase、prepare_redeem、finish。

模型负责理解与表达；Agent程序负责状态、参数、推荐匹配、确认和执行编排；银行程序负责权威测评、资源归属、资金规则、事务和落库。任何一方都不能把“模型说成功了”当成银行执行结果。

## 八、测试环境和验证方法

### 8.1 三层测试不能互相替代

1. **Agent离线层：** 网络禁止，脚本模型、HTTP替身；验证决策和状态，不证明数据库。
2. **银行集成层：** 指定PostgreSQL测试库和隔离schema，验证迁移、SQL记录、约束、事务、API。项目Database明确要求PostgreSQL，不用SQLite替换后声称等价。
3. **真实HTTP端到端层：** 银行独立进程连接该测试schema，Agent在自身工程进程调用；模型可以先脚本再真实。这里验证最终主路径和重启。

“真实HTTP＋脚本模型”证明链路和数据行为；“真实HTTP＋真实模型”补自然语言能力验收。银行业务数据仍为模拟，两者都不接真实资金。

### 8.2 安全的数据库准备与清理

- 执行前核对TEST_DATABASE_URL，不能默许仓库默认共享地址就是安全测试目标；输出中不展示密码。
- 只在当前测试创建并记录的schema中迁移、初始化和查询断言；确认银行测试进程也使用相同schema，防止测试断言和实际服务指向不同库。
- 银行已有fixture会创建／删除测试schema，了解其范围再复用；不要运行与本任务无关的数据库清理逻辑。
- 测试服务停止后才能清理自己的schema；严禁任意枚举并清理他人schema。
- 真实服务重启指停止并重启本次受控测试进程，保持原数据库和schema，不在重启时重新初始化样例。
- 本轮文档调整不执行以上数据库操作，后续实施需要的连接权限按环境申请。

### 8.3 数据库核验建议

每笔申购核验：accounts余额、holdings新仓、orders的product_purchase、transactions扣款、audit_logs动作、idempotency_records回执。

每笔赎回核验：accounts入账、holdings剩余本金／价值／状态、orders的product_redeem及收益分摊、transactions入账、审计和幂等。

失败核验：上述资金业务表无半完成变化；允许出现失败审计和安全计数。核实查询失败时不能以本地缓存替代数据库成功证据。

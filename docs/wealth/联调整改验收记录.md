#### P1-a：UNKNOWN 不再被折叠成失败

原来的实现把 `WealthStatus.UNKNOWN` 映射成 `TurnStatus.FAILED`（摘要如实，但状态是失败）。
`TurnStatus` 只有四个取值，所以"结果未知"只能落进失败——Supervisor 的模型、`domain_results[].turn_status`
以及任何按状态分支的调用方都会把它读成一次失败。**这是资金安全缺陷**：把一笔可能已经成交的交易
报成"没办成"，用户会去重新下单。

修复分三处：

- `app/agents/turn.py`：新增 `TurnStatus.UNKNOWN = "unknown"`。`TERMINAL_TURN_STATUSES` 由枚举派生，
  所以它自动成为终态——领域报出未知之后不会被重新派发（重复派发一次资金写是更坏的结果）。
- `app/agents/supervisor.py`：`_TURN_EVENT_STATUS[TurnStatus.UNKNOWN] = ToolStatus.FAILED`。
- `app/modules/wealth/application/turn.py`：`_STATUS[WealthStatus.UNKNOWN] = TurnStatus.UNKNOWN`，
  并删掉原先那条"塞进 FAILED"的分支。

**处置口径（W01-Q3，依 2026-10-13 提交 `03fd141`）**：只读回合允许出现 `tool_call`／`tool_result` 帧；以 interrupt（提问卡）结束的回合**也会**发出 `subtask_end`——它的 `turn_status` 是 `waiting_input`、摘要就是那句追问（事件层的 `status` 仍是冻结词表里的 `SUCCEEDED`）；承载查询结果的那条 `turn_status=completed` 子任务行属于**用户答完追问后的完成轮**。所以首轮按方案要求先追问三件事、以提问卡结束时，报告里那句“没有 wealth · SUCCEEDED 子任务行”与事件流不符——该轮确实发出了 `subtask_end`（`status=SUCCEEDED`、`turn_status=waiting_input`、摘要就是那句追问）；第一轮真正缺的是**承载查询结果**的那条 `turn_status=completed` 子任务行，它属于用户答完追问后的完成轮。处置仍是**不是缺陷**：设计把查询结果放在完成轮，首轮只负责追问。

**残留限制（如实记录，未掩盖）**：`subtask_end.status` 的事件词表被 `docs/ARCHITECTURE.md` 冻结为
`SUCCEEDED/FAILED/DENIED`（`ToolStatus`，属公共工具协议），没有"未知"这一值。所以活动流事件里
`unknown` 只能显示为 `FAILED`；**真正的"未知"经 `domain_results[].turn_status = "unknown"` 传给
Supervisor 的模型，用户读到的最终回复由模型按它如实转述**。要修到事件层，必须先改共享 `ToolStatus`
与冻结的事件契约，那是一次单独的、有意的决定（不在本轮范围）。这一取舍在代码注释与
`tests/test_domain_turn.py::test_every_turn_status_has_an_event_status` 里都钉住了。

**边界说明**：交接文档 §8 任务 1 写的是"不改 TurnHandler/TurnStatus"。本轮为修这个资金安全缺陷
改了 `TurnStatus`（以及 `tests/test_turn_contract.py` 里钉住取值集合的那条断言）。`TurnHandler` 的
三参数签名**没有**动。这是一次有意的、最小的越界，理由如上；如果评审认为应当保持 `TurnStatus`
不变，那么正确的替代做法是把 P1-a 记录成一条新的外部依赖（与 C1 同级），而不是继续把未知报成失败。

#### P2-b：追问声明改为必填

`ask_user.missing` 原本可选，程序只在模型**点名**时检查"是不是在重复追问已经知道的信息"。模型
省略它，这项检查就完全落空——"已知信息不重复问"退化成一句纯提示词建议。

修复：`missing` 改为必填（可以是空数组），并明确两条机械规则——名字必须在 `ASKABLE_SLOTS` 里；
不能点名已经知道的槽位。**问题本身仍然自由**（问卷的某一题、含糊的金额、任何澄清都能问），
不在补槽位就写 `[]`；这一条由 `test_a_free_question_with_an_empty_declaration_stays_valid` 证明。

**这条边界的反面也说清楚**：程序无法从自由文本里读出"这句话是不是又在问金额"，所以它保证的是
"模型必须声明、且声明里不能有已知信息"，而**不是**"任何措辞都不会重复问"。一个声明 `[]` 却去问
已知槽位的模型仍然绕得过去——那是一次蓄意的假声明，schema 拦不住，只能靠提示词与复核。

#### P2-a：预览的固定读取是规格授权的操作不变量

申购预览固定读产品／账户／测评，赎回预览固定读持仓／产品／账户。核对结论：**成立，但不是缺陷**。
计划 §3.2 第 6 条原文："`prepare_purchase`／`prepare_redeem` 由模型决定何时申请。缺业务槽位时返回
缺项供模型追问；**必要的交易预检与确认后的写前刷新可以由程序固定执行**。这些是操作不变量，不是
用户意图路由。" 第 7 条同时要求资金写、确认授权、幂等键与身份不能交给模型生成。

所以边界是：**模型决定要不要申请这一次预览**（它自己选工具、选时机），而"申请一次预览必须先看
哪些事实"是这笔操作的定义。让模型挑要读哪几项，等于给它机会跳过风险与余额校验。这与 `recommend`／
`compare` 那种"缺证据就交回模型"的处理并不矛盾：那两处是分析，读什么由需求决定；这里是交易前置
条件，读什么是不变量。本轮补了两条回归用例把这件事钉住
（`test_a_purchase_preview_reads_what_the_model_never_asked_for`、
`test_a_redeem_preview_reads_its_pre_check_and_never_the_risk_profile`），
并在两个节点的 docstring 里写明了规格依据。

### 2.2 本轮修复的失败回归（交接文档第 7 节 R01）

对话 #59 的失败有两个成因，都在范围内修掉了：

## 3. 外部依赖未满足（不阻塞范围内交付）

### C1：前端 → 主助手的可信按钮事件通道

**状态：未解除。** 主助手那条通道只传字符串，没有按钮事件与确认卡片返回协议，`TurnStatus` 也没有
`waiting_confirmation` / `unknown`。

本次交付的是**理财接收端**：`kind=confirm` / `kind=cancel` / `kind=reconcile` 三个受控输入、
确认卡片投影（`WealthResponse.confirmation`）、以及完整的状态机与测试。缺的是接入方那一半：
鉴权入口把按钮事件传进来、把卡片渲染出去。

因此经主助手发起的申购／赎回预览仍然被如实撤下（`TurnStatus.UNSUPPORTED`），
**这不是"暂时失败"，而是这条通道当前确实走不通**。用例：`test_c11_the_whole_turn_channel_still_refuses_a_write`、
`test_c11_a_chat_message_cannot_forge_a_confirmation_through_the_turn`。

理财内部接收契约已就绪：把 `wealth/application/turn.py` 的 `_to_result` 里那条 UNSUPPORTED 分支
换成"把 `waiting_confirmation` 交给调用方"即可，运行时的状态机不用改。

### D2：银行无验证码写能力

**状态：未解除。** `bank_backend/app/domain/investment_service.py::_require_verification` 同时要求
`confirm=true` 与 `mfa_code == settings.mock_mfa_code`，不按金额分级，也没有小额免验证。
银行后端不在本次修改范围内。

本次的处理是**如实报告能力**而不是绕过去：

- `WealthBank` 协议新增 `supports_click_confirmation()`；`HttpWealthBank` 回答 `False`。
- 点击确认在**发出任何资金请求之前**返回 `status=failed`、`error_code=invalid_state`、
  `reason_code=confirmation_transport_unsupported`，待办保留到 TTL。
- 不硬编码或猜测模拟验证码，不自动读银行配置或数据库取码，不把 confirm 偷偷转成带固定码的 verify，
  也不删除银行校验。
- 该分支不触发任何"验证码失败计数"，也不锁定用户：它根本不是一次资金请求。

用例：`test_c03_the_current_bank_refuses_before_any_fund_write`、`..._does_not_count_as_a_verification_failure`、
`..._the_http_adapter_reports_the_capability_it_really_has`；成功路径用测试替身
`support.ClickConfirmationBank` 验证，该替身**不证明当前银行兼容**（C02 与 C03 分开断言）。

### 结论

**在当前银行实现不变的前提下，本轮交付了理财确认协议与范围内逻辑，但不能诚实承诺"点击后真实
HTTP 成交"已经打通。** 接入方提供无验证码银行能力（或用户另行授权具体的模拟适配方案）之后，
换一个回答 `True` 的适配器即可完成真实成交验收，运行时不用改。

而这条行为正是同一个文件里 `pausable_gateway` 自己的文档所描述的。

修它需要改共享路由测试的夹具（把工具也授予 `transfer`，或让先下结论的领域换成 `bill`），
属于交接文档第 1 节列为「不修改」的共享区域，且与本轮"工具选择／外层记忆／确认接收"无关，

也没有为它们改动共享路由。它们各自的既有行为测试保留原样；如果"主模型编造入口"仍需要非记忆类的
公共逻辑改动，那是一条越界依赖，单独记录而不顺带修改（交接文档 §7 的要求）。

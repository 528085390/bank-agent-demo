## 4. 五个性质逐条结论

| # | 性质 | 结论 | 建立它的原始观察 |
| --- | --- | --- | --- |
| 1 | 用户原话经**普通消息路由**到达模块（无测试专用入口） | **已证实** | `POST /conversations/{id}/messages` 带用户原话 → SSE 里出现 `tool_call`(`subscription_list`)，随后 `tool_call`(`subscription_pause`) → `interrupt` 卡片。脚本没有调用任何模块内函数，只有公开 HTTP 路由 |
| 2 | 写请求停卡，卡片在**刷新／进程重启**后仍能从 checkpoint 读回 | **已证实** | §3.5：卡由 82792 建立，进程被 `Stop-Process -Force` 杀死后由 100404 提供 `GET /conversations/{id}`，读回**同一** `pending_id`／`question_id`／`expires_at`；S03 另有同一进程内的刷新读回 |
| 3 | 聊天框打"确认"**不是**授权 | **已证实（但表现是 409 拒绝，不是"当成普通消息处理"）** | §3.3：`POST /messages` `message="确认"` → `409 INVALID_INTERRUPT_ANSWER`，银行 0 次写，卡片仍开、id 未变。注意：基座在"有待回答问题"期间对普通消息是**拒绝**（409），并没有把它当普通轮次交给模块；规格 §"聊天里打确认不算授权"要的"不授权"成立，"当普通消息"不成立——见 §7 |
| 4 | 只有按钮事件 `POST …/decide` 会写，且双击只提交一次 | **部分证实** | "只有按钮"成立：整轮里唯一到达 `subscription_execute` 的路径是 `decide`（SSE `tool_call`）；聊天路由从未到达它。"写成功"不成立：写请求因 §5 的缺陷在审计层抛错，银行一行未动。"双击只提交一次"成立：同 `Idempotency-Key` 第二次返回 `duplicate:true`，银行 0 次写 |
| 5 | 已确认的 pause/resume 后银行表显示新状态；从未确认的预览后银行无变化 | **负半已证实／正半未证实（被 §5 阻断）** | 负半：S02/S08 卡片建立前后银行行都是 `status=active amount_minor=2900 last_charge_id=None next_due_date=2026-10-01`。正半：S06 点击确认后银行行**仍是**同一行（写请求根本没到银行），因此无法观察"新状态" |

## 5. 本轮发现的缺陷（**未修**，按任务6约束只报告）

**缺陷一：`agent_run_event.call_id` 列宽 64 装不下订阅工具的调用号，5/7 个订阅工具连审计都写不进去。**

- **位置：** `backend/app/storage/models.py:333` —— `AgentRunEvent.call_id: Mapped[str | None] = mapped_column(String(64))`。
- **机制：** 监督器把调用号铸成 `f"{agent_id}:{tool_name}:{uuid4().hex}"`（`backend/app/agents/supervisor.py:1356` 的 key 与 `:1373` 的 `call_id`）。`agent_id='subscription'`（12 字符）时，长度 = 46 + `len(tool_name)`。`ToolGateway.invoke` 先记审计、后调适配器：`backend/app/tools/gateway.py:209` `self._record_call(handle, invocation)` 在 `:215` `self._adapter.invoke(invocation)` **之前**；`:297-325` 的 `_record_event` 调 `self._audit.record_agent_event(...)`，而 `backend/app/audit/service.py:200-238` 的 `record_agent_event` 用 `with self.database.sessions.begin() as db: db.add(row)` 提交。于是审计 INSERT 先抛 `psycopg.errors.StringDataRightTruncation`，适配器根本没机会运行。
- **实测长度：**

  | 工具 | 调用号长度 | 结果 |
  | --- | --- | --- |
  | `subscription_list` | 63 | 可用 |
  | `subscription_pause` | **64（正好卡在边界）** | 可用 |
  | `subscription_detail` | 65 | 失败 |
  | `subscription_cancel` | 65 | 失败 |
  | `subscription_resume` | 65 | 失败 |
  | `subscription_charge` | 65 | 失败 |
  | `subscription_execute` | 66 | 失败 |

- **影响：** `subscription_cancel` / `resume` / `charge` / `detail` 连确认卡片都发不出来（审计先崩，图到不了 `wait`）；`subscription_execute` 无法写银行。这正是 S06 点击确认后银行不动的直接原因，也是 S09/S10-③ 的原因。`subscription_list` 与 `subscription_pause` 恰好可用，所以"停卡"看得见、"写"看不见。
- **为什么以前没暴露：** 基座其它领域的工具名更短（例如 `wealth` 前缀 + 工具名仍在 64 以内），只有订阅模块这一组名字踩线；`subscription_pause` 是 64，差一个字符就会一起坏。
- **可见性问题（次要）：** `backend/app/api/sse.py:64-65` 的 `logger.error("stream_failed request_id=%s type=%s", request_id, type(exc).__name__)` 没有 `exc_info`，正常日志里只有 `type=DataError`，看不到 `psycopg` 那句话。本次是用一个**仓库外**的诊断入口（`D:\ai_project\_diag_stream.py`，给 `sse.logger.error` 包了一层 `traceback.print_exc()`）才拿到 §3.6 的堆栈；**生产代码一行未改**。
- **次要观察：** 失败的轮次会提交一行 `RUN_FAILED` 审计，其 `error_code='9h9h'` 是 SQLAlchemy 的错误链接码，不是领域错误码；会话随后 `recovery_required: true`。

### 缺陷二：唯一对真实银行发 HTTP 的订阅测试期望过期，默认路径永远跳过它（**未修**）

## 7. 本轮发现并修复的问题（都在本任务范围内）

1. **赎回的验证码话术说成了申购。** `application/runtime.py` 的 `VERIFICATION_PROMPT` 是固定
   字符串"…以提交这笔模拟申购"，赎回时会对用户说错方向。已改为按 `operation` 措辞
   （申购／赎回），并在 §6 的真实赎回会话里复核到正确文案。
2. **提示词对赎回的编号来源说得不够明确。** `llm/prompts.py` 里申购那条明写"先 call_read 产品
   列表和账户列表"，赎回那条只说"编号只能来自已经查到的持仓"。真实模型因此在"赎回"这一轮
   偶尔直接引用持仓号而不先查一次，被运行时按"引用了工具没有返回过的编号"拒绝。已把赎回那条
   补成"先 call_read 持仓列表／账户列表"，修复后 ③ 层 44 项全通过。
3. **验收需要"起点是对的"这条断言。** 验收会真的改钱，所以 `test_acceptance.py` 在模块开始时
   断言专用 schema 处于刚 seed 完的状态（余额、样例持仓、无历史理财订单），不满足就带着重建
   命令失败，而不是留下一串误导性的余额断言失败。
4. **交互式入口把用户输入吞进缓冲区，一个字都不处理**（交付后手动验收时发现）。
   `cli.run_session` 第一行是 `pending = list(lines)`，而交互模式的输入是**无限生成器**
   （`_interactive_lines` 循环调用 `input()`）：`list()` 因此永不返回，用户每句话都被攒进
   列表，终端只反复出现 `你: ` 提示符、看不到任何回复，直到 Ctrl+C 才一次性回放。
   它还有第二个副作用：从 stdin 读时 `list(sys.stdin)` 会**提前吃掉后面那一行验证码**，
   使非交互申购必然失败。已改为只持有迭代器、处理完一句才取下一句，并且**先判断要不要
   验证码、再取下一行**，把验证码那一行留给 `read_code`。
   这个缺陷逃过了 ① 层原有用例，因为那些用例给 `run_session` 传的都是有限列表
   （`[]`、`["退出"]`），`list()` 不会卡住。已补 2 项会变红的回归
   （`test_interactive_line_is_processed_before_the_next_prompt` 断言第二次读输入之前第一句话
   已被交给 Agent 并渲染；`test_stream_input_leaves_the_verification_code_for_the_code_reader`
   断言 stdin 里的验证码不被聊天输入吃掉）；两者在修复前均失败，修复后 ① 层 281 → **283 项**。
   真实模型 + 真实银行复跑一次只读查询，回复正常（正确列出 `p_demo_cash` 并识别
   `p_demo_closed` 已停售）。

  只跳过"库内订单／幂等记录"的断言，HTTP 与余额断言仍然执行——这一条在记录里明确标注。
- **真实模型的措辞不固定**：A14 断言的是业务不变量（预览金额、余额、订单、无未授权写），不是
  模型的固定话术。观察到过一次模型把"已成交"误读成"还在等确认"并要求澄清（钱没有动，属于
  模型侧的状态理解偏差）；真实用户会再说一遍，验收里对"补齐信息"和"赎回"这两轮各允许一次
  同义重述，用尽仍失败即判失败。
- **Agent 重启会丢会话**：临时待办、槽位与"本进程写锁定"重启即丢，用户需要重新发起并确认；
  这是设计选择（银行事实才是权威），不是缺陷。
- **本模块没有接入主智能体与前端**：`wealth` 未注册为平台业务工具，也未改 Supervisor 路由；
  集成属于后续工作（A15 已证明独立路径不依赖它们）。
- **专用 schema 已在验收结束后删除**：`DROP SCHEMA "test_wealth_accept_5e3ddb9f" CASCADE`；
  本轮没有对共享库或其他人的 schema 做任何清理。
